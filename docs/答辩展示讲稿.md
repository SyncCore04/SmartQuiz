## 1. 演示前 10 分钟准备清单

按顺序做完，逐项打勾。

- [ ] **① 启动小程序后端**：双击根目录 `start-backend.bat`，看到窗口打印 `服务启动：http://127.0.0.1:5000` 才算成功。这个窗口**不要关、不要最小化到任务栏看不见的地方**（答辩时可能有人要看日志）。
- [ ] **② 启动管理后台**：双击根目录 `start-admin.bat`，看到 `地址 : http://127.0.0.1:5001` 成功。同样保留窗口。
- [ ] **③ 浏览器提前登录后台**：打开 `http://127.0.0.1:5001`，用 `admin` / `admin123` 登录，**停在数据看板页**。不要现场输密码，容易打字出错或卡顿。
- [ ] **④ 微信开发者工具**：导入 `front/` 目录 → 「详情 → 本地设置」勾选**不校验合法域名、web-view（业务域名）、TLS 版本以及 HTTPS 证书** → 编译一次确认首页正常出数据。
- [ ] **⑤ 小程序端预热一次**：随便进一次答题页并提交一次，确认判分和结果页正常。**不要留一个空白的答题页**。
- [ ] **⑥ 浏览器多开标签页**：把后台的数据看板、题目管理、题库挂载三个页面各开一个标签页，演示时直接切换，省去点击导航的时间。
- [ ] **⑦ 关掉干扰**：微信、QQ、系统通知、其他编辑器窗口全部关闭或静音；把浏览器和开发者工具都放大到合适字号（**评委在后排要能看清**）。
- [ ] **⑧ 准备两套数据说明**：当前数据库里已有 1 个用户、5 条答题记录、47 条错题。如果评委问「数据是不是写死的」，就用这些真实历史记录回答。
- [ ] **⑨ 备份预案**：提前把演示过程录屏一次存到桌面；并截图保存关键页面（首页、答题、结果、错题本、统计、后台看板、题目管理）。
- [ ] **⑩ 报告在手**：把 `SmartQuiz_课程设计报告第二版.docx` 打开放在旁边，被问到设计细节时可以翻到对应章节。

## 3. 逐幕讲稿

### 第 1 幕 · 开场（30 秒）

**操作**：不切屏，站着说。PPT 或报告封面停在小程序首页截图。

**【说】**

> 各位老师好，我做的项目是 SmartQuiz 在线答题系统。
>
> 它解决的是学生刷题的四个具体问题：题目散落在课本和文档里不好找、做完要自己逐题对答案、错题没有地方沉淀、学习效果没法量化。
>
> 我的方案是：**微信小程序 + Flask 后端 + SQLite 数据库**，学生端负责刷题和考试，后端负责判分和统计，另外我还配套做了一个 **Web 管理后台**，让题目的维护不用再改代码。
>
> 下面我按「系统怎么搭的、学生怎么用、老师怎么管」三个部分演示。

---

### 第 2 幕 · 架构与技术选型（1 分钟）

**操作**：打开后台数据看板页停留（或切换到架构图）。

**【说】**

> 系统是前后端分离的三层结构。
>
> **前端**是微信小程序原生框架，一共 10 个页面，底部三个 Tab：首页、考试、我的。引入了 Vant Weapp 组件库改善界面表现。
>
> **后端**是 Python 的 Flask 框架，一共 13 个接口，统一用 `{code, data, msg}` 的 JSON 格式返回，`code` 等于 0 表示成功。
>
> **数据库**是 SQLite，通过 Python 标准库 `sqlite3` 直接访问，**没有用 ORM**，一共 10 张表，题库里有语文、数学、英语、理综四个学科共 60 道题，覆盖单选、多选、判断、填空四种题型。
>
> **管理后台**也是 Flask，但用的是 Jinja2 服务端渲染，独立跑在 5001 端口，和 5000 端口的小程序接口完全不干扰，而且**我没有修改小程序后端的一行代码**。
>
> 这里要特别说明一个设计取舍：我没有用 MySQL、没有用 ORM、也没有上前端框架，因为项目规模不大，我希望把「请求 → 判分 → 落库 → 统计」这条主链路做扎实，用最基础的标准库反而更能体现对底层的理解。整套系统**只依赖 Flask 一个第三方库**。

---

### 第 3 幕 · 小程序端演示（3 分钟）

这一幕分三段，每段「做动作 → 说一句」。

#### 3-1 首页与题库（40 秒）

**操作**：切到微信开发者工具，首页 → 左右滑动热门题库 → 点一个学科分类 → 在题目列表点题型筛选标签（比如「多选」）。

**【说】**

> 这是首页，从上到下是学习数据概览、轮播图、学科分类宫格、公告和热门题库。
>
> 这里所有数据都是**实时从后端接口拿的**，不是写死在前端的——我现在点一个分类进去，可以看到题目列表，顶部可以按单选、多选、判断筛选，这个筛选是在前端基于已获取的数据完成的，响应很快。
>
> 注意一个细节：**题目接口返回的数据里不包含答案和解析**。这一点是故意这么设计的，后面讲判分的时候我会说明原因。

#### 3-2 答题与判分（核心，1 分 30 秒）

**操作**：点一道题进入答题页 → **故意答错两题、答对三题**（嘴里念出来哪题故意选错）→ 点提交 → 结果页出现 → 指着分数讲。

**【说】**

> 答题页支持单选互斥选择、多选切换、判断二选一，底部可以点题号在题目之间跳转。
>
> 现在我做五道题，其中**我故意答错两道**，然后提交。
>
> ——分数出来了：60 分，对了 3 道、错了 2 道。
>
> 这里我重点讲**判分是在服务端做的**。前端只把「题目编号 + 我选的选项」提交给后端，后端逐题去数据库查标准答案，把两边都转成大写再比对，所以答案大小写不影响判定；多选题是把选中的字母排序后拼成一个字符串，和标准答案直接比对，所以选的顺序也不影响。
>
> 为什么判分一定要放在后端？因为如果在前端判分，标准答案就必须下发到客户端，**抓包就能直接拿到答案**。所以题目接口刻意不带 `answer` 和 `analysis` 字段，判分只能发生在服务端。
>
> 成绩计算是「正确数 ÷ 总题数 × 100」四舍五入，同时把这一条答题记录写进数据库。

#### 3-3 错题本与学习统计（50 秒）

**操作**：结果页 → 点「查看错题」或切到错题本页 → 展示刚才那两道错题 → 切到学习统计页 → 展示正确率、连续天数和本周柱状图。

**【说】**

> 刚才答错的两道题，**已经自动进错题本了**，不需要我手动录入。可以看到每题都有我的答案、正确答案和解析。
>
> 这个自动收集发生在提交判分的同一个请求里：判分时发现哪题答错，就把题干、我的答案、正确答案、解析一起写进错题表。如果同一道题重复答错，走的是更新逻辑而不是插入，**所以错题本里不会出现重复的题**。
>
> 再看学习统计：累计答题数、整体正确率、连续打卡天数，还有本周每天的答题量柱状图。
>
> 这几个指标全部是后端算好直接返回的，前端只负责画出来。比如连续天数，是把我的答题日期去重排序后，从最近一天往前数「日期差正好一天」的连续段长度。

### 第 4 幕 · 管理后台演示（3 分钟）

**操作**：切到浏览器后台标签页。这是**加分幕**，务必留足时间。

#### 4-1 为什么要做后台（30 秒）

**操作**：停在数据看板页。

**【说】**

> 接下来是这次重点新增的管理后台。
>
> 做它是因为原来加一道题的流程是：改代码文件里的题库 → 删掉数据库 → 重启后端。**删库会把所有答题记录和错题本一起清空**，这在演示的时候非常尴尬。
>
> 现在改成在网页上点几下就行，而且**不用重启、不用删库、不丢任何已有数据**。
>
> 这是数据看板：用户数、题目总数、累计答题题次、总体正确率，下面是各学科的题目分布柱状图，还有最近的答题记录。

#### 4-2 题目管理改一道题（1 分 30 秒）★核心动作

**操作**：切到题目管理页 → 用「关键词」搜一道题 → 点编辑 → **改掉题干里的一个字**（比如加个「（已修改）」后缀）→ 保存 → 提示「题目已保存」→切回微信开发者工具 → 刷新题目列表 → **指着改动给评委看**。

**【说】**

> 这是题目管理，支持按分类、题型、难度、关键词四种条件筛选，而且是**服务端分页**，不是一次性把所有题拉到前端。
>
> 我现在搜一道题出来，编辑它，改一下题干，保存。
>
> 注意看提示：「题目已保存」。现在**我不重启任何服务**，直接切回小程序端刷新一下——
>
> ——题目已经变了。
>
> 这就是前面说的：后台改的是小程序**实时读取的同一张表**，而题目接口每次请求都是实时查库，所以改完立刻就生效。原来需要「改代码 + 删库 + 重启」三步，现在一步都不用。

#### 4-3 挂载关系与数据一致性（1 分钟）

**操作**：切到题库列表 → 点某一题库的「挂载题目」→ 展示勾选列表和已选计数 → 不保存，直接讲；再切到考试列表展示状态标签。

**【说】**

> 题库和题目、考试和题目都是**多对多**关系，靠中间表维护。后台的挂载页把全部题目列出来勾选，保存的时候是「整体替换」——先清掉这个题库原有的全部关联，再写入当前勾选的结果，这样界面显示和数据库里一定是一致的。
>
> 这里有个**容易被忽略的点**：首页分类宫格上显示的题目数、题库卡片上的题目数，在数据库里是**冗余存储**的字段。如果后台加了题但不去更新它们，小程序端显示的数字就会和实际题目对不上。所以我在后台每次增删题目或者改动挂载关系之后，都会用一条带子查询的 UPDATE 语句**重新算一遍**这三个统计字段。
>
> 还有一个坑：**SQLite 默认不开启外键约束**，所以删题目的时候，中间表里的关联记录不会自动清理，会留下「题库挂着一个已经不存在的题」这种脏数据。我在后台删除题目时手动清理了两张中间表，再删题目本身，并且同时重算统计字段。
>
> 另外，如果某个分类下面还有题目，后台会**拒绝删除**并给出提示，防止误操作把题目变成孤儿数据。

### 第 5 幕 · 亮点与难点（1 分 30 秒）

**操作**：不切屏，正对着评委说。这一段是**拿分点**，语速可以放慢。

**【说】**

> 最后我想讲三个我认为做得比较好的地方，以及开发中遇到的一个问题。
>
> **第一，零侵入的架构设计。** 管理后台对原有代码的唯一依赖，就是导入后端里的数据库路径常量和连接函数，**小程序后端 `app.py` 一行都没有改**。两个服务是两个独立进程、独立端口，共读同一个数据库文件。这样做的好处是：后台万一出问题，不会影响小程序端的正常演示。
>
> **第二，数据一致性是我主动处理的，不是碰巧对的。** 冗余计数的重算、删除时的手动级联清理、有题目的分类禁止删除、挂载时对提交的题目编号做有效性校验——这些都是我在设计阶段就考虑到并专门写代码处理的。
>
> **第三，功能写完不是终点，我用自动化测试把容易出错的路径跑了一遍。** 后台的冒烟测试覆盖了 **73 项断言**，包括鉴权拦截、7 个模块 14 个页面的渲染、题目新增的三类校验分支、答案和选项的归一化、挂载结果与勾选是否一致、删除后关联是否被清理、批量导入遇到非法行是否跳过并给出原因。而且**测试是跑在数据库副本上的，真实数据一行都没动**。
>
> **开发中遇到的一个问题**：小程序首页曾经整个白屏，控制台报 `@babel/runtime/helpers/arrayWithHoles.js is not defined`。排查后发现是开发者工具的**增强编译**功能会把代码里的解构语法编译成对 `@babel/runtime` 的依赖，但这个包并不存在于 `miniprogram_npm` 里。因为我的代码只是普通的 ES6 语法，不需要增强编译，所以关闭这个选项后问题解决。这件事让我意识到：**报错信息指向的往往不是真正的根因，要顺着依赖链去找。**

### 第 6 幕 · 收尾（30 秒）

**【说】**

> 总结一下：SmartQuiz 完成了需求分析里提出的全部功能，包含 10 个小程序页面、14 个后台页面、13 个后端接口、10 张数据表和 60 道题目，「登录 → 答题 → 判分 → 错题 → 统计」这条闭环完整可跑通，判分结果和人工核对一致，管理后台的修改能被小程序端即时读取。
>

>
> 这些是我下一步的改进方向。
>
> 以上是我的汇报，请老师提问。

## 5. 千万不要做的事

| 不要做 | 原因 |

| ❌ 现场删 `database/smartquiz.db` | 会清空全部演示数据，当场没有退路 |

## 6. 高频追问与应答

答不上来时统一话术：「这部分我目前是在 XX 层面实现的，还没有做到 YY，是我下一步的改进方向。」**坦承边界比硬编更得分。**

**Q1：为什么用 SQLite 不用 MySQL？**
> 因为这是单机演示项目，SQLite 零安装零配置，整个数据库就是一个文件，拷走项目就能跑。表结构和 SQL 写法和 MySQL 基本通用，将来数据量大了迁移成本很低。

**Q2：为什么不用 ORM、不用前端框架？**
> 项目规模小，我想把最基础的链路讲透。手写 SQL 用 `?` 占位符参数化，能直接体现防注入的做法；前台用服务端渲染而不是单页应用，省掉了构建流程和一堆依赖。整套系统只依赖 Flask 一个第三方库。

**Q3：判分为什么不在前端做？**
> 前端判分就必须把标准答案下发到客户端，抓包就能拿到答案，等于没有考试意义。所以题目接口刻意不带 `answer` 和 `analysis` 字段，判分只能在服务端。

**Q4：多选题怎么判对错？**
> 前端把选中的选项字母排序后去重，拼成比如 `AC` 的字符串；后端把标准答案和用户答案都转成大写，然后直接字符串比对。所以多选题的**选择顺序不影响**判定。

**Q5：答案大小写不一样算错吗？**
> 不算。两边都做了大写转换再比对，所以提交小写 `b` 和正确答案 `B` 是判对的。

**Q6：错题本会自动去重吗？**
> 会。写错题之前先按「用户 + 题干」查一次，已经存在就执行 UPDATE 更新我的答案和时间，不存在才 INSERT。所以同一道题反复答错，错题本里只有一条。

**Q7：管理后台会不会影响小程序？**
> 不会。后台是独立文件、独立进程、独立端口 5001，它对现有代码的唯一依赖就是导入数据库路径和连接函数。`app.py` 一行都没改，后台挂了也不影响小程序演示。

**Q8：加题流程现在是什么样的？**
> 以前是「改题库文件 → 删数据库 → 重启」，删库会连答题记录一起清空。现在在后台网页上增删改就行，**不用重启、不用删库**，因为题目接口每次请求都实时查库。

**Q9：那 `questions_data.py` 还有用吗？**
> 有用，但角色变了。它现在是「初始数据快照」，只在全新环境首次建库时灌数据。它的**元组格式同时也是后台批量导入支持的粘贴格式**，可以直接复制粘贴进去。

**Q10：后台删一道题会不会留下脏数据？**
> 不会，但需要手动处理。SQLite 默认不开启外键约束，所以我在删题目之前先清理 `bank_question` 和 `exam_question` 两张中间表，再删题目本身，最后重算统计字段。

**Q11：分类宫格上的题目数是怎么来的？**
> 数据库里 `category` 表有一个冗余的 `count` 字段。后台每次增删题目或改动挂载关系后，都会用相关子查询重新计算一遍。如果漏了这一步，小程序端显示的数字就和实际题目对不上——这是我最开始差点漏掉的地方。

**Q12：后台的登录是怎么做的？**
> 用 Flask 的 session 保存登录标记，账号密码配在配置文件里，密码用 `werkzeug` 的哈希函数以 pbkdf2:sha256 存储和比对，**不保存明文**。为了避免新增模块时忘记加权限校验，我没有逐个视图加装饰器，而是在应用入口注册了一个全局拦截，**默认所有页面都要登录**，只放行登录页和静态资源。

**Q13：管理员账号只有一个是吧？**
> 是的，这是我**有意做的简化**。管理员就一个，为它建一张表反而增加复杂度。真实系统应该改成管理员表加角色字段，支持「超管 / 出题老师」这种权限区分，这是我下一步要做的。

**Q14：连续打卡天数怎么算的？**
> 把该用户所有答题记录的日期去重排序，从最近有记录的那一天往前数，日期差正好等于 1 天就继续往前，遇到断档就停止，累计的长度就是连续天数。

**Q15：测试做了多少？怎么做的？**
> 小程序接口部分用黑盒测试，向后端发真实 HTTP 请求，15 个用例覆盖首页、筛选、判分、错题、统计和异常参数。后台部分用 Flask 的测试客户端做了自动化冒烟测试，**73 项断言全部通过**，而且跑在数据库副本上，不动真实数据。

**Q16：数据表之间是什么关系？**
> `user` 对答题记录和错题是一对多；`category` 对题目是一对多；题库和题目、考试和题目都是多对多，各自用一张中间表实现；轮播图是独立的辅助表。

**Q17：如果上线要做哪些改动？**
> 小程序端把接口地址改成服务器地址并配置 HTTPS 合法域名；后端换成 gunicorn 之类的生产服务器；数据库迁移到 MySQL 并加索引；登录换成微信授权加 token 鉴权；后台补上多管理员、角色权限和操作日志。

**Q18：Vant 组件库你用了哪些组件？**
> 实际只用了它的 **Icon 图标组件**。题目里的分类图标、菜单图标用的是 Vant 的图标名。界面布局和交互是我自己用 WXML 和 WXSS 写的，没有直接用它的表单、弹窗这些组件。

## 7. 应急预案

| 情况 | 处理 |
|------|------|
| 小程序首页空白 | 检查后端窗口是否还在跑。若已崩溃，口述「后端服务刚才意外中断」，同时切到浏览器演示后台（后台是独立进程，通常还活着） |
| 后端窗口报错退出 | 直接双击 `start-backend.bat` 重启，趁重启时说「首次初始化会重建数据库，稍等几秒」 |
| 后台打不开 | 大概率是 5001 端口被占。改用截图讲解，**不要**在现场排查端口 |
| 提交后卡在「判分中」 | 立刻点一次别的页面再回来；仍然失败就直接切后台演示，别说「怎么又坏了」 |
| 数据看起来是空的 | 用后台数据看板证明数据库里有真实数据，再解释小程序端可能是没登录态 |
| 时间被压缩到 5 分钟 | 直接跳到「4 分钟压缩版」动线 |
| 被问到没做过的功能 | 「这个功能目前还没实现，是我下一步的计划」——**不要编** |
| 完全答不上来 | 「这个问题我回去确认一下再答复老师」比乱说好 |
